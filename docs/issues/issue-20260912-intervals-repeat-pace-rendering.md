# Intervals repeat and absolute-pace rendering

## Incident

On 2026-09-12, applying the approved Week 3 plan created its targetless long
run successfully but blocked the repeated pace workout during semantic
readback. The provider returned four executable steps instead of the six
prescribed steps. Its parsed document omitted both the two-repeat structure and
the 5:10-5:20 per-kilometre target.

The publication remained in pending owned state. The semantic guard was not
weakened and the malformed remote workout was not accepted as equivalent.

## Root cause evidence

The exact rendered workout placed repeat children under indented lines without
blank-line boundaries around the repeat block. It also emitted an absolute pace
range as `5:10-5:20/km` without the provider's required `Pace` marker.

Intervals.icu's current workout-builder guide requires an empty line before and
after each repeat block, states that nested repeats are unsupported, and shows
absolute pace using the explicit `Pace` marker. The live provider readback
matched those documented failure modes: no repeat count, no pace target, and a
different step order.

References:

- <https://forum.intervals.icu/t/workout-builder/1163>
- <https://forum.intervals.icu/t/workout-builder-syntax-quick-guide/123701>
- <https://forum.intervals.icu/t/specify-workouts-using-absolute-pace/115846>

## Decision

Render repeat blocks in the provider's documented flat, blank-line-delimited
form and include `Pace` for every absolute pace target, including ramp targets.
Reject nested repeats before any provider mutation. Keep semantic readback
strict and retain the pending owned event until an athlete-confirmed drift
resolution can safely replace it after the renderer fix is validated. When a
renderer revision changes generated bytes, establish pending authority from the
immutable applied-workout lineage and discover the exact event from its owned
identity; do not rewrite or falsely certify the old pending representation.
Bind any replacement consent to a fresh fingerprint of the complete remote
event.

Renderer-independent recovery still requires the pending UID and external ID
to equal the deterministic identity derived from the retained local workout.
This prevents corrupt pending metadata from redirecting a confirmation or
retirement operation to a different Resilio-namespaced event.

Apply the same state-evolution rule when the pending workout is removed from the
active week. An exact future target may be deleted after confirmation and moved
to durable deletion monitoring. An exact past target is instead rewritten to
the current renderer representation, verified, and retained as historical
publication evidence. Search pending-only ownership identities provider-wide
and reject duplicates even when one claimant is outside the scheduled week.
If the retained workout itself is no longer representable losslessly, do not
delete or certify a past event and do not issue a drift-confirmation token that
cannot resolve it; report a publication-safety failure and retain both states
for an explicit plan correction.

Keep representation changes distinct from relevant sport-setting changes. If
the latter fingerprint changed, force a guarded upsert even when current remote
bytes happen to match; never persist the event as though it had been published
under the new settings.

The supported publication syntax currently represents absolute pace,
beats-per-minute, and watt targets as whole numbers. Reject fractional values in
those units before any remote mutation rather than silently rounding them and
creating a deterministic semantic-readback failure.

## Validation

- Add regression coverage for exact boundaries before and after a repeat,
  six-step expansion, and absolute pace syntax.
- Make the publication fake honor the documented repeat and pace grammar so it
  cannot accept the previous invalid rendering.
- Cover nested-repeat rejection, pace-ramp syntax, and fractional target
  rejection for every supported whole-number target unit.
- Cover the complete pre-change pending state through drift status, exact
  confirmation token, replacement, durable convergence, and final safe status.
- Cover renderer-superseded stale pending retirement for both a future event
  deletion and a past event correction/preservation. For retained shapes that
  the current renderer cannot represent, cover future confirmed deletion and a
  non-mutating past publication-safety stop.
- Reject an in-week pending identity when a second provider event claims the
  same owned identity outside the week.
- Cover interrupted pending recovery across a relevant sport-settings change
  and require a real upsert before persisting the new settings fingerprint.
- Run focused publication, scheduling-adoption, and architecture quality gates.
- Reconcile the exact owned Week 3 event only through the existing drift
  confirmation workflow.

Final local validation on 2026-09-12: 143 focused publication and schedule
regressions passed, all 16 architecture tests passed, all 874 repository tests
passed, Ruff reported no lint errors, mypy reported no errors across 240 source
files, and the diff whitespace check passed. Red/green regressions first
reproduced the malformed repeat/pace readback, active and stale pending renderer
evolution, provider-wide duplicate identity, relevant sport-setting changes,
unrepresentable future/past legacy states, and corrupt deterministic pending
identity before their corresponding fixes were applied.
